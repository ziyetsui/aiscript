# Ancher Scripter 性能提速方案

日期：2026-10-10。审查基线：8f9d1f8。

本方案来自对 Claude 性能文章、huashu-flash 的 README、SKILL、测量协议、招式库和 benchmark/ratchet 脚本，以及本项目关键调用路径的阅读。第 1–5 节记录优化前的审查和计划；第 6 节记录第一轮实施与隔离测试结果。尚未取得真实用户耗时分位数，下文不把静态分析估计或函数计数当成实测速度倍数。

## 1. 应用文章的方法，而不是照搬所有招式

文章的提速对象是启动、导航和交互等用户旅程，并不意味着模型推理速度提高三倍。对本项目最有价值的方法是：定义用户可感知的终点，区分客户端和服务端，建立可重复基线，小步优化，验证实际收益，并用稳定的计数防止回退。

本项目应分别跟踪：启动到能输入、打开项目到能编辑、按键到画面更新、发送到首段可见回应、发送到全部修改可编辑、点击导出到文件可用。一个“生成完成”状态不能代表这些不同终点。

huashu-flash 是性能工作流和测量脚本，不是安装后会自动加速的运行时依赖。它默认的 Chromium 网页、Fast 4G、CrUX 口径不能直接代表打包后从本地文件加载的 Electron 应用。它适合成为开发辅助工具，不需要放进客户安装依赖，也不需要加入产品的“原型建模”创作 skill。

## 2. 已确认的优先改进点

### A. AI 生成完成后仍逐字播放整个新增剧本

位置：`apps/desktop/src/renderer/src/screens/Workspace.tsx` 的 `send`、`typeOut` 和 `shown`。

目前先等待 `ai.write` 完成，再读取全部项目状态，随后隐藏新增节点并按节点顺序逐字展示。每个节点每次暂停 16ms，展示完再暂停 60ms；长段落也会有接近 60 次展示更新。这不是模型正在生成，而是已经到达客户端的文本再次播放。

代码中的标称等待公式为：

```text
step = max(1, ceil(文本长度 / 60))
单节点标称等待 = (floor(文本长度 / step) + 1) × 16ms + 60ms
总标称等待 = 各新增节点等待之和
```

例如 100 个节点，每个 100 字，标称定时器等待为 87.6 秒。这是说明机制的合成例子，不是用户现有剧本的实测；实际耗时还受定时器、渲染和设备影响。短角色名与短对白的等待会小得多。

建议：默认立即显示已提交的所有节点，保留修改标记和短暂高亮。手动输入的打字机音效继续仅响应可信用户输入。若保留 AI 展示动画，应给整轮设置总预算，允许跳过，并在新请求、分集切换和卸载时取消旧播放；不再给每个节点单独累加预算。

验收：收到成功结果后，全部节点在下一次正常渲染中可访问；撤销仍以整轮为单位；新输入、切换分集和导出不会受到旧动画影响。

### B. 一个流式片段或一个输入动作更新整个工作区

位置：`Workspace.tsx` 的顶层 `stream`、`input` 状态、`onDelta`、`chatPanel`；`components/Chat.tsx` 的 `AssistantMessage`；`lib/markdown.tsx`。

每个 AI delta 调用顶层 `setStream`，输入框的每次修改也调用顶层 `setInput`。工作区重新执行，遍历聊天历史、节点和 mentions；完成的 AI 消息重新进入 Markdown 解析和元素构建。聊天消息回调、附加内容等引用也在重新构建。

准确区分：当前流式 `Thinking` 显示的是文本，不是每个片段都解析流式 Markdown。这里优先解决的是顶层更新带来的历史消息和编辑器重复工作。

建议：

1. 将输入草稿状态放到输入组件附近，将实时回应放到独立组件或按请求订阅的存储中。
2. delta 到达时先缓存，最多每个动画帧合并一次可见更新；结束、取消和错误时立即刷新尾部，不能丢最后一段。
3. 已完成消息正文按文本版本缓存；为回调和辅助属性维持稳定引用，避免只加 `memo` 却仍传入全新对象。
4. mentions 在角色、地点、笔记集合变化时重建。
5. 滚动跟随只在可见内容高度变化且读者位于底部时触发；按帧合并高度读取和滚动写入。
6. 更长历史再考虑按窗口渲染。先处理重复渲染，避免直接虚拟化破坏浏览器搜索、复制、滚动锚点和无障碍体验。

验收：输入草稿不重新解析历史 Markdown；只收到新片段时，已完成消息正文不重新解析；滚动阅读历史时不强制拉到底；取消与队列顺序保持不变。

### C. 每次编辑都返回整个项目状态

位置：`screens/Editor.tsx` 的 `onText`、`flush`；`Workspace.tsx` 的 `edit`；`main/projects.ts` 的 `edit`、`state`。

编辑器修改本地节点后立即 flush 到主进程。主进程提交 Loro 编辑，并返回完整 `ProjectState`；构造状态会读取节点、各分集统计、素材、聊天历史等。文本编辑的返回值又更新工作区状态。随着项目增长，单字编辑承担了越来越多与该字无关的遍历、对象分配和 IPC 序列化。

已经存在的优化：落盘在最后一次编辑后合并等待 400ms。因此不能笼统说“每个键都同步写硬盘”；主要需要先消除每个编辑的完整状态构造与传输。

建议：文本编辑返回轻量确认，例如版本号、编辑序号及必要的局部统计；结构性变化返回增量或按需更新。保证过期确认不会覆盖较新的本地输入。保持导出、切换、关闭前的 flush 屏障。后续如果要合并 IPC，必须先明确确认和落盘语义，不能简单增加防抖时间来换取丢字风险。

额外发现：`Line` 已经使用 `memo`，但 Editor 中传递的事件函数随渲染重新生成，仍可能使未修改行重新渲染。应稳定回调并验证实际 render 次数。结构性编辑的 `s.nodes.map(...live.find...)` 可以先建立 Map，将二次遍历变成线性合并。

验收：单字编辑响应大小不会随聊天记录增长；旧响应不覆盖新输入；中文输入法、粘贴、Enter、Backspace、撤销以及输入后立即导出都保留最新内容。

### D. 打开项目时重复请求完整状态

位置：`Workspace.tsx` 初始化与页面上下文相关的 effects。

初次挂载有两个 effect 分别调用 `projects.open`；AI 状态检查发现空闲时也再调用一次。主进程已有打开项目缓存，所以这不等于每次重新读盘，但完整状态构造和 IPC 返回仍会重复。

建议：明确唯一的初始加载入口；将“状态是否忙”“页面参考变化”“项目内容发生变化”拆开处理。没有内容变化时不重读全部项目；确有外部写入时按项目版本刷新。给竞争请求设置版本或取消保护。

验收：空闲项目初次打开只做一次完整加载；笔记处理、外部工作流写入及分集切换仍正确刷新。

### E. 启动加载与持久化是第二轮的测量对象

启动：`renderer/src/App.tsx` 同步导入多个功能页面；激活状态及 key 状态未返回时渲染为空。可以先显示稳定的应用外壳，再按需加载低频页面和重型功能。权限与草稿恢复仍需完成后才允许相应操作。`main/index.ts` 的主进程启动依赖也应通过启动 profile 找出需要延迟加载的服务。

已经做到：同一项目切换页面时 Workspace 保持挂载，保留对话和撤销状态。应保留，不需要重做。

持久化：`main/projects.ts` 保存完整 Loro 快照、元数据以及镜像文件；`main/local-data.ts` 使用同步 SQLite，每次保存还检查已有每日备份。大项目可能出现主进程停顿，需要真实数据测量其持续时间。

如果确认是瓶颈，再设计后台持久化队列或独立进程，并保留错误回传、保存顺序、退出与导出的屏障、备份恢复和崩溃一致性。不要先关闭 fsync、降低 SQLite 同步等级或取消备份。

V8 code cache、静态 composer、worker 和编辑器虚拟化都可以作为后续候选，但应由 profile 决定。当前有更直接的重复工作可消除。

## 3. AI 生成速度单独处理

当前写作链路：Ancher SDK 发起与接收远程生成，Mastra 写作工作流负责本地编排和校验，合法 ops 再进入 Loro 文档。更换编排框架不一定缩短远程模型时间。

建议记录以下时间段，跨进程使用请求 ID 关联，分别记录进程内耗时；跨进程或远程时间戳需要统一时间基准，不能直接相减不同的 `performance.now()`：

```text
点击发送
→ 本地附件与参考准备结束
→ SDK 请求发出
→ 首个有效文本片段到达
→ 首段有意义的回应可见
→ 远程生成结束
→ 校验结束（单列修复请求）
→ ops 原子提交完成
→ 全部结果可编辑
```

重点检查三个方向：

- 上下文预算：当前剧本最多 12,000 字符，大纲和节拍各最多 6,000 字符，skill 总预算 18,000 字符，另有世界观和参考资料。它们不是 token 数，应记录实际长度及服务支持的 token usage。按修改目标选择相关材料；保留需要的节点 ID、证据和规则，不能靠粗暴截掉逐字稿来提速。
- 写作请求在 `ai.ts` 中只要存在写入目标，就会选择完整协议头。因此并非所有后续请求都仅发送短提醒。先验证服务支持的会话、系统提示词或缓存机制，以及省略协议后的正确率，再决定优化；本地字符串缓存也不等于服务端 prompt cache。
- 修复率：校验不通过可能触发额外生成。统计修复比例和耗时，提升首轮结构合法性与目标完整性，能减少整轮模型请求。不能关闭校验，也不能把澄清等待当成非法输出修复。

对“原型建模”：研究阶段保存有证据和适用边界的模型；原创生成阶段根据用户要求引用相关模型，不必每次都重新生成完整十部分研究报告。这是任务分阶段与成果复用，不是降低分析质量。

流式正文可以提前展示；结构化 ops 仍应完整解析、校验后原子提交。不要为了“看起来快”直接修改半截 JSON，也不要展示未完成的任意推理内容。

目前没有 Ancher 服务端 profile、排队和模型推理指标，不能承诺客户端改动把模型生成速度提高三倍。

## 4. 为这个项目建立测量台

| 旅程 | 起点与终点 | 同时收集的计数 |
|---|---|---|
| 冷启动 | 启动进程 → 恢复后的输入框可用且新字符保留 | 主进程启动阶段、模块载入、初始 IPC |
| 项目打开 | 点击项目 → 正确分集内容可编辑 | 全量 open 次数、响应字节、state 构造次数 |
| 文本编辑 | 可信输入 → 下一次显示更新 | 未修改行 render、完整 state 返回、IPC 字节 |
| 草稿输入 | 输入聊天草稿 → 新字符可见 | 历史 Markdown 解析、工作区 render |
| 长回复 | 固定 delta 序列 → 全部回应可见 | 完成消息解析、每帧提交、滚动更新、长任务 |
| AI 写入 | 固定合法结果到达 → 全部修改可编辑 | 人工播放预算、提交次数、状态读取次数 |
| 导出 | 点击确认 → 可打开的完整文件 | 等待保存时间、导出各阶段与结果一致性 |

测试数据至少包括：小项目、长剧本、多分集、长聊天与多个 FPAE 报告、较多素材。使用固定隔离数据副本，不能让 benchmark 修改用户项目。

本地交互使用固定模拟 SDK 消息，隔离模型随机性；远程请求用另一组测试评估端到端体验。记录失败、取消和修复比例，不能排除失败样本后声称整体更快。

使用正式构建而非 Vite 开发模式作为主要结论；区分新进程冷启动与同进程热切换，不混合不同缓存条件。每组至少 10 次报告 p50/p75/p95；10 次仅够初步判断，尾部结论应增加样本。优化前后交替配对，记录设备、版本、窗口、数据规模和负载。

同时测试默认动效与 reduced motion。现有部分写作 E2E 使用 reduced motion，会跳过 `typeOut`，因此功能通过不能证明默认展示速度合理。

时间指标用于配对评估与趋势告警；渲染次数、IPC 请求数、解析次数等稳定指标用于回归门槛。至少用两项优化证明所选计数与真实耗时同向变化，避免把无关计数做成目标。不要让一次幸运的毫秒结果自动降低整个项目的时间阈值。

隐私：默认记录长度、计数、耗时、版本和错误类型，不记录剧本正文、笔记内容或 key。真实用户遥测应另行设计透明的授权和数据策略。

## 5. 推荐实施顺序

1. **测量基线**：建立上述旅程和隔离数据；先记录现状。
2. **第一轮三个小 PR**：取消整轮逐字等待；消除重复项目打开；隔离输入和流式状态，缓存完成消息。分别测量贡献，不把所有收益归到一个大改动。
3. **第二轮编辑链路 PR**：轻量编辑确认、稳定行回调、线性节点合并；覆盖输入法和立即导出的完整性。
4. **第三轮按 profile 决定**：启动按需加载、后台持久化、较长列表渲染等。
5. **AI 链路实验**：统计上下文、首字、修复请求与总时长；再做目标化上下文和模型成果复用。

每轮保留：本地输入可靠性、单轮撤销、原子写入、澄清回复与恢复、笔记两种来源、分集归属、导出内容、取消和重启恢复。交付时同时报告速度与正确性，不用“按钮早出现”代替“能正确操作”。

暂不设置三倍等收益承诺。第一轮的明确目标是：已经到达的剧本立即可用；输入与流式更新不重复处理整个历史；没有内容变化不反复获取完整项目。真实改善比例在配对测量后填写。

## 6. 第一轮实施与验证

已实现：取消生成结果的逐字播放，保留新增节点与预览修改的高亮；初次项目完整加载合并为一次；草稿和流式展示分别由独立组件管理；完成消息的 Markdown 按文本缓存；mentions 按数据变化重建。页面上下文改变时仍刷新项目，曾处于忙碌状态的外部任务结束时仍刷新结果。

草稿和当前请求的文本缓冲由项目工作区保留，因此对话移入侧栏或切回写作页时不会丢失。流式展示按动画帧合并，并过滤其他请求与 ops 内容；最终回复仍以主进程保存的完整消息为准。模型、写作协议、校验和持久化机制没有改动。

新增 `apps/desktop/e2e/performance.e2e.ts`：启动真实 Electron、renderer、IPC 和 Loro，只替换远程 SDK 服务，使用临时数据目录，默认动效开启。通过 V8 precise coverage 统计实际函数执行，并先用一次真实渲染验证计数器能看见相关函数，防止“没有采集到”被误当成零开销。初次读取次数在真实 IPC 边界统计。

同一场景的优化前后观察：

| 指标 | 优化前 | 优化后 |
|---|---:|---:|
| 空闲项目初次完整读取次数 | 3 | 1 |
| 输入 8 个字符：Workspace 执行次数 | 8 | 0 |
| 输入 8 个字符：历史 Markdown 执行次数 | 8 | 0 |
| 30 个流式片段：Workspace 执行次数 | 35 | 0 |
| 30 个流式片段：历史 Markdown 执行次数 | 30 | 0 |
| 120 段提交后当下可见的节点 | 1 | 120 |
| 120 段提交后完整且可编辑的节点 | 0 | 120 |

这些是隔离功能场景的计数与可用性观察，基线及新版各一次，不是十轮配对耗时统计，也不是线上速度结论。Workspace 可能因合法活动状态变化执行，因此流式计数测试在活动已稳定、远程响应尚未结束的区间采样。

额外验证包含：草稿跨页面保留、流式前缀在侧栏保留、最后一个片段与 done 紧邻到达时尾部完整，以及 120 段的一次整轮撤销。性能回归脚本已加入 macOS/Windows E2E 工作流。

本地复现：

```bash
pnpm --filter @scripter/desktop e2e:performance
```

本轮没有实现第 C、E 节的轻量编辑 IPC、启动加载及后台持久化，也没有实施 AI 上下文实验；它们保留为后续按测量推进的工作。
